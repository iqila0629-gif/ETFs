# 交付物整理经验

> 日期：2026-08-07
> 背景：v4 基金预测项目从建模到最终交付，最后阶段反复整理交付包，耗时较多。
> 结论：交付物应该边做边归纳，方案尝试必须留痕，但留痕要轻、要可读、要能复现。

## 一、这次踩过的坑

1. 最后才整理交付包。
   数据、脚本、中间结果、对照版本散落各处，最后集中打包时才发现缺文件、
   文件太大、命名不一致、流程对不上。

2. 方案尝试没有及时归纳。
   原版、方案A、互补、m20、m25、m30 每个版本都跑过，但结论分散在多个报告里，
   最后要重写一份说明才能讲清楚“为什么选 m30”。

3. 把历史过程整包塞进去。
   一开始把 v3 中间文档全部复制进交付包，绕了弯路，包又大又乱。
   交付包应该只保留“从原始数据到最终成果”的直路，历史过程放在项目仓库留痕即可。

4. 报告太多、不可读。
   MD 报告对上司不友好，最终要合并成一份纯文本说明，
   用表格和结论讲清楚每个方案、每个指标、为什么选这个方案。

5. 大文件没有提前处理。
   穷举扫描的 CSV 动辄几 MB 到十几 MB，最后又要删掉改由脚本再生成。

6. 命名不统一。
   文件名带 `v4_` 前缀、中间结果命名不一致，交付时还要逐个改。

## 二、以后怎么做：边做边归纳

### 1. 项目一开始就定交付结构

```text
项目根目录/
├─ 数据/
│  ├─ 数据_原始/
│  └─ 数据_处理后合并/
├─ 中间文档/
│  ├─ 文件/
│  └─ 脚本/
├─ 成果/
│  ├─ 正式版/
│  └─ 对照版本/
└─ 说明.txt
```

### 1.1 双轨制：工作区是原版，交付包是快照

- 工作区（项目仓库）保留方便实际使用的原版：数据、脚本、中间结果都留在原地。
- 交付包（例如 `最新结果/`）是给上司的可读、留痕副本，强调可读性和留痕，
  但不一定是最方便使用的版本。
- 每个新文件生成时，把一份可读副本复制进交付包；工作原版不要移走。
- 交付包可能被移动、压缩或删除，所以不能把交付包当作唯一版本，
  也不要直接在工作流程里读写交付包。
- 实际使用请用工作区的原版；交付包只负责展示和存档。

### 2. 每个方案尝试都留痕

每跑一个新方案，固定记录：

```text
方案名：
时间：
参数/思路：
关键指标：Average、命中率、交易数、冻结期交易数、吞没率等
产出文件：
结论：达标/淘汰
淘汰原因：
```

不要只留 CSV，要把“为什么做、结果如何、为什么不用”写进一份说明。

### 3. 对照版本要轻

- 每个对照版本只放公司格式 Excel 和一份简短说明。
- 中间 CSV 不进对照版本，能由脚本再生成就不打包。
- 历史版本不要整文件夹塞进交付包，仓库 git 历史本身就是留痕。

### 4. 大文件只留脚本

- 穷举扫描、全量面板、合并池等大文件不放进交付包。
- 交付包保留：原始数据、必要输入、小体积中间结果、脚本。
- 每个可再生成文件标注“由哪个脚本生成”。

### 5. 命名从第一天就统一

- 文件名不加临时前缀。
- 版本用明确后缀：正式版 / 方案A / m20 / m25 / m30。
- 中间结果命名与脚本输出一致，避免“同名不同内容”。

### 6. 交付说明要合并成一份可读文本

- 不要丢一堆报告。
- 用一份纯文本说明讲清楚：
  1. 试过哪些方案
  2. 每个方案的思路和核心指标
  3. 为什么选最终方案
  4. 每个目录是干什么的
  5. 每个脚本的输入输出

### 7. 包内流程要闭环

- 所有输入都要在交付包内。
- 所有中间输出统一写一个目录。
- 最终输出单独放“成果”。
- 每个脚本写清楚：作用、输入文件、输出文件。

## 三、下次项目建议顺序

1. 数据到位后先定目录结构。
2. 每完成一个扫描/方案，立刻写一行结论并放好产出。
3. 每完成一个扫描/方案，立刻把可读副本复制一份进交付包。
4. 每周整理一次“方案尝试表”，避免最后翻记录。
5. 交付前只做一次“打包”，不做“考古”。
6. 打包检查清单：
   - 文件命名统一
   - 大文件已删除并标注生成脚本
   - 输入输出闭环
   - 一份说明讲清所有方案和选型
   - 无多余报告
   - 对照版本只留公司格式和说明

## 四、核心原则

```text
边做边整理，不最后考古；
方案留痕，但留痕要轻；
报告给机器，结论给人；
大文件靠脚本，小文件靠打包；
目录结构第一天就定，命名第一天就统一。
工作区是原版，交付包是快照；
交付包可能被移走，所以永远不放进交付包里工作。
```
